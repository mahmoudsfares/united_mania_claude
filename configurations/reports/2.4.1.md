## A design decision this subtask needed

Changing `getNews()` to take a page number risked breaking `NewsFeedCubit` and its test today,
even though the cubit itself is not this subtask's job (it's 2.4.3's). `news_feed_cubit_test.dart`
constructs the cubit with `NewsFeedMockRepo().getNews` as a torn-off function, and `NewsFeedCubit`
currently expects that function to take zero arguments.

Making the new parameter `{int page = 1}` (optional, defaulting to page 1) rather than
`{required int page}` solves this for free: a function with only optional parameters can still be
assigned wherever a zero-argument function is expected, so the cubit's existing zero-argument call
keeps compiling and behaves exactly as before (page 1, same as today). This is not just a
compile-time trick — `1` is also NewsAPI's own documented default for the `page` query parameter,
so the default is a faithful match to the real API, not a local workaround. Confirmed with
`flutter analyze` (see below): no changes were needed anywhere outside the mock repo and its test.
2.4.2 will use the same `{int page = 1}` shape on `NewsFeedRepo` for the same reason.

  - `getNews()` → `getNews({int page = 1})`.
  - New fixture `static const Map<String, dynamic> successResponseBodyPageTwo` — same shape as
    `successResponseBody` (`JsonKeys.status` + `JsonKeys.articles`), four more invented Manchester
    United articles, keys from `JsonKeys`.

    since it carries no JSON parsing edge case. The one-second delay and the `returnError` flag

- `test/features/news_feed/business_logic/news_feed_mock_repo_test.dart` — rewritten. See below.

  `configurations/features_description/work_breakdown.md` — updated as described above, ahead of
  any code.
- No other file changed. `news_feed_repo_test.dart` and `news_feed_cubit_test.dart` needed no
  edits — confirmed by `flutter analyze`.

## What was tested

- `getNews(page: 1)` still returns the original ten articles after at least a one-second delay.
- `getNews(page: 2)` returns the four new articles.
- `getNews(page: 3)` returns an empty success list.
- `returnError: true` returns the fixture's error message for both page 1 and page 2, proving the
  flag ignores the page argument.

  (mirroring the existing check on `successResponseBody`).
- The four pre-existing `successResponseBody` tests (ten articles, the null-`urlToImage` case, the
  `"[Removed]"` title case, the null-`author`/null-`source.id` case) are unchanged and still pass.
