# 3.1.3 — Open in browser

## What was asked

Add the hyperlink that opens the full article in the device's browser: a thin `UrlLauncherApi`
wrapper over `url_launcher`, a `NewsDetailsCubit`/`NewsDetailsState` driving `openArticle(String?
url)`, and the "Read the full article" link on the details screen with a `BlocListener` scoped to
just the link that shows a snackbar on failure. This is the last piece of the details screen — both
screens are complete after this subtask.

## What changed

- `lib/core/apis/url_launcher_api.dart` — new. `UrlLauncherApi.launch(String url, {required
  LaunchMode mode})`, a one-line wrapper around `launchUrl`. Its only job is to exist as an
  injectable seam so the cubit never touches a platform channel in tests.
- `lib/features/news_details/business_logic/news_details_state.dart` — new. `typedef
  NewsDetailsState = StateResource<void>;`.
- `lib/features/news_details/business_logic/news_details_cubit.dart` — new. `NewsDetailsCubit`
  takes the launch function through its constructor (the same functional-injection pattern
  `NewsFeedCubit` already uses for its repo method, rather than injecting the whole `UrlLauncherApi`
  object). `openArticle(String? url)`: a null/empty url emits `AppErrorMessages.noArticleLink`
  without calling the api; otherwise it calls `_launch(url, mode: LaunchMode.externalApplication)`
  and emits success, or `AppErrorMessages.couldNotOpenLink` on a `false` result or a thrown error.
  No loading state — the spec's behaviour table only describes error/success, so none was added.
- `lib/features/news_details/news_details_screen.dart` — rewritten from a `StatelessWidget` into a
  `StatefulWidget` taking `article` and `cubit`, matching the disposal pattern `NewsFeedScreen`
  already established in 2.5.1. `dispose()` calls the new `AppDi.disposeNewsDetails()`. Appended the
  hyperlink after the content section: a `BlocListener<NewsDetailsCubit, NewsDetailsState>` wrapping
  only an `InkWell`/`Text("Read the full article")`, listening for `state.isError` to show a
  `SnackBar`. The link's colour comes from `Theme.of(context).colorScheme.secondary` — no inline
  colour literal.
- `lib/core/di/app_di.dart` — added `newsDetailsCubit` (lazily builds `NewsDetailsCubit(const
  UrlLauncherApi().launch)`) and `disposeNewsDetails()`, side by side with the existing news feed
  pair. Unlike the feed, this wires the **real** `UrlLauncherApi` by default — opening a real
  browser costs nothing and is the correct production behaviour, unlike hitting the rate-limited
  news API, so there is no mock/real swap here.
- `lib/core/routing/app_router.dart` — the `Routes.newsDetails` case now passes `cubit:
  AppDi.newsDetailsCubit` into `NewsDetailsScreen`.
- Tests:
  - `test/features/news_details/business_logic/news_details_cubit_test.dart` — new. The four
    scenarios from the subtask spec: a valid url calls the api once with
    `LaunchMode.externalApplication` and emits success; a null url and an empty url each emit
    `noArticleLink` and never call the api; a throwing api and a `false`-returning api both emit
    `couldNotOpenLink`. Uses a `mocktail` mock of `UrlLauncherApi`.
  - `test/features/news_details/news_details_screen_test.dart` — every existing test now goes
    through a `_pumpScreen` helper that builds a `NewsDetailsCubit` with a stub launch function
    (mechanical fix for the new required `cubit` parameter). The two tests that counted `Text`
    widgets were updated for the now-always-present hyperlink (3→4, 1→2). Added one test asserting
    the link renders and that tapping it calls the cubit with the article's url.
  - `integration_test/features/news_details/news_details_screen_test.dart` — added the two
    end-to-end scenarios from the subtask spec: tapping the hyperlink passes that article's url to
    the launcher, and a failing launcher shows the snackbar. Both pump `NewsDetailsScreen` directly
    with a fake launch function (bypassing `app.main()`/`AppDi`, matching news_details.md §2's "no
    mock repo, tests inject a fake `UrlLauncherApi`") rather than driving the real app, since the
    real `AppDi.newsDetailsCubit` would try to open a real browser. The existing navigation test's
    duplicated fixture-parsing code was pulled into a shared `_firstMockArticle()` helper.
  - `test/core/routing/app_router_test.dart` — `tearDown` now also calls
    `AppDi.disposeNewsDetails()`, since building the details route touches that singleton too.

## What was tested

- `flutter analyze` — no issues found (run by me).
- Confirmed by you: `flutter test` and `flutter test
  integration_test/features/news_details/news_details_screen_test.dart`, both green, after two
  rounds of fixing the new widget-level hyperlink test.
- The new tests failed first as expected (they referenced `NewsDetailsCubit`/`UrlLauncherApi`/the
  `cubit` parameter before those existed).
- One real debugging detour worth recording: the widget test that taps the hyperlink kept failing
  even after implementation, because `_fullArticle`'s full content (image + title + byline + date +
  description + a full paragraph) pushes the link below the default 800×600 test viewport, and
  `tester.tap()` was landing on a point with nothing hit-testable there. Adding `ensureVisible()`
  before the tap did not fix it either. The reliable fix was to stop depending on scroll/visibility
  mechanics altogether: the three tests that tap the hyperlink now resize the test viewport
  (`tester.view.physicalSize = const Size(800, 3000)`) before pumping, so the link is always on
  screen.
