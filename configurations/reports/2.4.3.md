# 2.4.3 — Paginate `NewsFeedCubit` and `NewsFeedState`

## What was asked

The last of the three pagination subtasks (after 2.4.1's mock repo and 2.4.2's real repo): make
`NewsFeedCubit` track the current page and know when to stop. `NewsFeedState` stops being a bare
`typedef` for `StateResource<List<Article>>` and becomes a small `Equatable` class wrapping that
resource plus two flags, `isLoadingNextPage` and `hasReachedMax`, exposing the same
`isInit`/`isLoading`/`isSuccess`/`isError`/`data`/`error` getters as before plus `copyWith`.
`getNews()` keeps meaning "page 1 / refresh"; a new `getNextPage()` requests `currentPage + 1`,
guarded against firing while a load is in flight, after `hasReachedMax`, or before the first page
has loaded successfully.

## Design decisions this subtask needed

**The injected function had to grow a `page` parameter.** Since 2.2.1, the cubit has taken the
repo's `getNews` method torn off — `Future<NewsFeedState> Function()` — rather than a repo object,
because `NewsFeedRepo` and `NewsFeedMockRepo` share no common type (see that report). Now that
`getNextPage()` needs to ask for a specific page, that function type became
`Future<StateResource<List<Article>>> Function({int page})`. No change was needed to either repo:
both have taken `{int page = 1}` since 2.4.1/2.4.2, and a function with only optional parameters is
still assignable wherever this shape is expected — the same reasoning already used twice in this
task, confirmed again by `flutter analyze` touching neither repo file.

**`getNews()` now calls `_getNews(page: 1)` explicitly, not `_getNews()`.** This matters for the
mocked-repo tests: a `mocktail` mock has no real method body, so the `page = 1` default on the
interface is never applied when the call goes through `noSuchMethod` — `repo.getNews()` and
`repo.getNews(page: 1)` are different invocations as far as a stub is concerned. The old test
stubbed the bare call; it now stubs `repo.getNews(page: 1)`, matching what the cubit actually sends.

**The tracked page number lives only on the cubit, not in `NewsFeedState`.** Nothing the screen
renders depends on which page number is current, only on the article list and the two flags, so
adding a `currentPage` field to the public state would expose an implementation detail no test or
screen needs — against CLAUDE.md §4's "do not over-engineer".

**A failed `getNextPage()` does not advance the tracked page.** `_currentPage` only moves forward
inside the success-and-non-empty branch, so a retry after a failure asks for the same page again
instead of skipping it — matching `news_feed.md` §4: "If the next page fails, the indicator is
simply removed... scrolling to the bottom again retries."

**Test fixtures reuse the same `const Article` values across stub, seed, and expectation.** `Article`
still does not override `==` (noted in 2.2.1), so two independently-built lists of otherwise-equal
articles are never `==`. For the mocked-repo tests, reusing the same `const` `Article`/`NewsFeedState`
values everywhere makes the compared lists hold the same object references, so `Equatable`'s
element-wise comparison passes without needing `isA<...>().having(...)` partial matchers. The
real-`NewsFeedMockRepo` tests still use `having(...)` on `data?.length`, as 2.2.1 did, since those
articles come from independent `Article.fromJson` parses.

## What changed

- `lib/features/news_feed/business_logic/news_feed_state.dart` — rewritten from the `typedef` to a
  small `Equatable` class: `resource`, `isLoadingNextPage`, `hasReachedMax`, the six delegating
  getters, and `copyWith`.
- `lib/features/news_feed/business_logic/news_feed_cubit.dart`:
  - `_getNews` field type changed to accept `{int page}`.
  - `getNews()` resets `_currentPage` to `1` and emits a fresh loading state, then a fresh state
    wrapping whatever the repo returned — unchanged in effect from before.
  - New `getNextPage()`: guarded (see above), emits `isLoadingNextPage: true`, requests
    `_currentPage + 1`, then either appends the new articles and advances the page, sets
    `hasReachedMax` on an empty response, or just clears the loading flag on failure.
- `test/features/news_feed/business_logic/news_feed_cubit_test.dart` — rewritten. Three groups:
  - `getNews` with a mocked repo — success and error, unchanged in meaning from before 2.4.3, now
    against the class-shaped state and the explicit `page: 1` stub.
  - `getNextPage` with a mocked repo — appends on success, sets `hasReachedMax` on an empty page,
    clears the loading flag and keeps the list on failure, and three no-op cases (already loading,
    already at max, first page not yet loaded), the last three verifying the repo is never called.
  - Both methods against the real (now two-page) `NewsFeedMockRepo` — `getNews` success/error as
    before; `getNextPage` walking from page 1 (10 articles) to page 2 (14 total,
    `hasReachedMax` false) to page 3 (still 14, `hasReachedMax` true).
- No other file changed — `news_feed_repo.dart`, `news_feed_mock_repo.dart`, and the project's
  feature docs already described this shape from 2.4.1/2.4.2 onward.
