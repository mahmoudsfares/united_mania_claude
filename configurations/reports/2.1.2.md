# 2.1.2 — `NewsFeedRepo`

## What was asked

Fetch and parse the feed: `NewsFeedRepo.getNews()` returning `Future<StateResource<List<Article>>>`,
calling `AppDioClient.get` with the endpoint and query values from `ApiEndpoints`, mapping the
`articles` array to `Article` objects, and returning a success resource. Failures must be routed
through `networkErrorHandler` rather than assembled by hand. The dio client is injected through the
constructor so tests can mock it. Tests required: a 200 with two articles returns success with two
parsed articles; a 200 with an empty `articles` array returns success with an empty list; 401, 429,
and a timeout each return the matching error message.

## What changed

- `lib/core/networking/api_endpoints.dart` — added `qQueryParam`, `sortByQueryParam`,
  `languageQueryParam` (the literal query-parameter key names `'q'`, `'sortBy'`, `'language'`).
  These didn't exist yet: 1.3.3 only added the parameter *values* plus the `apiKey`/
  `apiKeyQueryParam` pair. Without the key-name constants the repo would have had to hardcode
  `'q'` / `'sortBy'` / `'language'` directly in its query map, which CLAUDE.md §4/§8 forbid ("no
  hardcoded ... map keys ... anywhere — pull them from core/utils / api_endpoints"). The new
  constants mirror the existing `apiKeyQueryParam`/`apiKey` naming pattern exactly.
- `lib/features/news_feed/business_logic/news_feed_repo.dart` — new. `NewsFeedRepo` takes an
  `AppDioClient` as a single positional constructor argument, stored in a private field.
  `getNews()` calls `_dioClient.get(ApiEndpoints.everything, queryParameters: {...})` with the
  three new constants, reads `response.data[JsonKeys.articles]` as a `List<dynamic>`, maps each
  entry through `Article.fromJson`, and returns `StateResource<List<Article>>.success(articles)`.
  Any thrown error — from the network call itself or a malformed body — is caught and delegated to
  `networkErrorHandler<List<Article>>(error)`; the repo never builds an error state itself, per
  CLAUDE.md §3.
- The constructor is positional (`NewsFeedRepo(this._dioClient)`) rather than a named parameter
  assigned in the initializer list. A named parameter
  (`{required AppDioClient dioClient} : _dioClient = dioClient`) tripped the
  `prefer_initializing_formals` lint, because it was a pure passthrough with no extra logic —
  unlike `AppDioClient`'s own `_dio = dio ?? Dio()`, which the lint leaves alone since that isn't a
  pure passthrough. The lint's own suggested fix is `this._dioClient`; used as a *named* parameter
  that would expose an awkward private-underscore label at call sites
  (`NewsFeedRepo(_dioClient: mock)` — valid Dart, but confusing to read). Making it positional
  keeps the initializing formal the lint wants without that oddity.

## What was tested

- `test/core/networking/api_endpoints_test.dart` — one new test asserting the three new
  query-parameter-name constants.
- `test/features/news_feed/business_logic/news_feed_repo_test.dart` — new. Uses `mocktail` to mock
  `AppDioClient` directly, rather than `http_mock_adapter` (which mocks at the raw-Dio transport
  level and was used only for `AppDioClient`'s own test in 1.3.3). `NewsFeedRepo` depends on our
  own `AppDioClient` class, so mocking that class directly is the natural boundary, and matches the
  subtask's own wording: "inject a mock." Covers: two articles parsed correctly from a 200
  response; an empty `articles` array returning an empty list; the exact query map sent to
  `AppDioClient.get` (captured with `captureAny`) matches `ApiEndpoints.q` / `sortBy` / `language`
  under the new key constants; a 401 failure returns `AppErrorMessages.invalidApiKey`; a 429
  failure returns `AppErrorMessages.rateLimited`; a connection-timeout failure returns
  `AppErrorMessages.timeout`.
- Confirmed the fail-first step: you ran the two test files before `news_feed_repo.dart` and the
  new `ApiEndpoints` constants existed, and got the expected failure.
- `flutter analyze` — no issues found (after switching the constructor to a positional
  initializing formal, see above).
- `flutter test` (full suite) — all passing, confirmed by you.

## Anything left open

None. The 400 path (raw API message passthrough) is already covered by
`network_error_handler_test.dart` from 1.3.2 and wasn't re-tested here, since the repo delegates
all error mapping to `networkErrorHandler` and adds no branching of its own — re-testing every one
of its branches through the repo would only duplicate that coverage. `NewsFeedMockRepo` (2.1.3) is
next in the work breakdown and was not touched.
