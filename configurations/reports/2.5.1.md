# 2.5.1 — App shell and the first working screen

## What was asked

The first subtask to put a screen on the device, and the first with an end-to-end test. Build:
`core/di/app_di.dart` (a static-singleton getter for the feed cubit, wired to `NewsFeedMockRepo`,
plus a matching dispose method); `core/routing/app_router.dart` (`generateRoute` with a
`Routes.home` case and a "route not found" default); `lib/main.dart` (`MaterialApp` with
`AppTheme`, `onGenerateRoute`, `initialRoute`); and `news_feed_screen.dart` as a `StatefulWidget`
that calls `getNews()` in `initState`, disposes the cubit in `dispose`, renders the four states
from `news_feed.md` §4 (loader, error view, empty message, plain `ListView` of titles), and wires a
`ScrollController` so scrolling near the end calls `getNextPage()`. Card styling is explicitly out
of scope here — that is 2.5.2.

## What changed

- `lib/core/di/app_di.dart` — `AppDi.newsFeedCubit` lazily builds a `NewsFeedCubit` against
  `const NewsFeedMockRepo().getNews`; `AppDi.disposeNewsFeed()` closes it and clears the singleton.
  Swapping in the real `NewsFeedRepo` is the one-line change CLAUDE.md §6 asks for.
- `lib/core/routing/app_router.dart` — `Routes.home` builds `NewsFeedScreen(cubit:
  AppDi.newsFeedCubit)`; anything else builds a `Scaffold` showing `AppStrings.routeNotFound`.
- `lib/main.dart` — `UnitedManiaApp` now builds a real `MaterialApp` (theme, initial route, route
  generator) instead of the empty one from 1.1.1.
- `lib/features/news_feed/news_feed_screen.dart` — the screen itself: `BlocBuilder` wraps only the
  `Scaffold` body; a `ScrollController` listener calls `getNextPage()` once scroll position is
  within 200px of the max extent; the list's last row is a small `AppLoader` while
  `isLoadingNextPage` is true.
- `test/core/di/app_di_test.dart`, `test/core/routing/app_router_test.dart`,
  `test/features/news_feed/news_feed_screen_test.dart` — unit/widget coverage for the three pieces
  above: singleton identity and disposal; the two routing branches; the four screen states plus the
  trailing loading row appearing and disappearing.
- `test/app_smoke_test.dart` / `integration_test/app_smoke_test.dart` — updated for the app no
  longer being an empty shell: they jump past the mock repo's one-second delay with a fixed
  `tester.pump(Duration)` rather than `pumpAndSettle`, since the loader's own animation keeps
  scheduling frames and never lets `pumpAndSettle` see the app as settled.
- `integration_test/features/news_feed/news_feed_screen_test.dart` — new end-to-end test: launch,
  loader, ten rows, scroll to load four more (fourteen total), scroll again once the mock's pages
  are exhausted (still fourteen); a second scenario drives the screen directly with a repo that
  fails once and recovers, covering the error view and Retry.

## Design decisions this subtask needed

**The end-to-end test's scroll simulation went through two failed attempts before landing.** The
first version sized the test surface to `700` tall on the assumption that a bare `ListTile` is 56px
tall, so ten rows (560px) would overflow it — they didn't (56px is the *minimum*, not the actual,
row height), so the list never became scrollable and the scroll-triggered `getNextPage()` never
fired. Shrinking the surface and switching to a bounded `drag` fixed that but broke differently: on
the real device the title text wraps across more lines than assumed, so even the *first* ten rows
didn't all fit inside `ListView.builder`'s viewport-plus-cache window, and some were dropped from
the tree before the first count assertion.

The fix that landed stops guessing row height entirely. The test now swings the surface between two
deliberately extreme sizes: a short one (`300` tall — guaranteed to overflow no matter how tall a
row turns out to be, so the list is scrollable and the pagination listener fires) while dragging,
and a tall one (`1200` — guaranteed *not* to overflow, so nothing is outside `ListView.builder`'s
cache) right before each `findsNWidgets` count. Neither size depends on the actual rendered row
height, which is why it holds up where the two previous attempts didn't.

**The DI and routing tests build the route's widget without mounting it.** Mounting
`NewsFeedScreen` calls `initState` → `getNews()`, which starts a real one-second timer through
`NewsFeedMockRepo` — irrelevant to proving the route table is wired correctly, so both tests in
`app_router_test.dart` call `AppRouter.generateRoute(...).builder(context)` and assert on the
returned widget's type/content without pumping it into a running tree.
