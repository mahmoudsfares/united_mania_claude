# 1.3.2 — NetworkErrorHandler

## What was asked

One place that turns a thrown failure into an error `StateResource`. The first pass mapped every
failure to a fixed message from `AppErrorMessages` and never showed the API's own `message` field.
After a follow-up review, that rule was refined: 400 is a request-shaped error whose text varies by
request (whichever parameter was missing), so it now shows the API's own message; 401, 426, 429,
and 5xx stay fixed, since each is one single, well-understood condition.

## What changed

- `lib/core/networking/network_error_handler.dart` — new. Top-level generic function
  `networkErrorHandler<T>(Object error)` (matching the call style `work_breakdown.md` uses for it
  in 2.1.2), returning `StateResource<T>.error(...)`:
  - `connectionTimeout`, `sendTimeout`, `receiveTimeout` → `AppErrorMessages.timeout`
  - `connectionError` → `AppErrorMessages.noInternet`
  - `badResponse` status `400` → the API body's own `message` (via `JsonKeys.message`), falling
    back to `AppErrorMessages.generic` if the body has no usable string there
  - `badResponse` status `401` → `AppErrorMessages.invalidApiKey`
  - `badResponse` status `429` → `AppErrorMessages.rateLimited`
  - `badResponse` status `>= 500` → `AppErrorMessages.serverError`
  - `badResponse` status `426`, any other status code, `cancel`, any other `DioExceptionType`, and
    any non-`DioException` object → `AppErrorMessages.generic`
- `lib/core/utils/json_keys.dart` — added `message`, the API error body's key, now that 400 reads
  it.
- `configurations/features_description/news_feed.md` §2 and `work_breakdown.md` 1.3.2 (and the
  `json_keys.dart` bullet in 1.2.2) — updated to describe 400 as the one exception to "never show
  the raw message," since the spec text no longer matched what the code does.

## What was tested

- `test/core/networking/network_error_handler_test.dart` — 18 tests, one per branch: the three
  timeout types, `connectionError`, `cancel`, four cases for badResponse 400 (a usable message
  shown as-is; a missing message, an empty message, and a non-map body all falling back to
  generic), status codes 401/429/500/503, an unmapped status code (404), `unknown`, a plain
  non-`DioException` `Exception`, and a check that 401 — one of the fixed-message codes — never
  leaks the API's raw text.
- `test/core/utils/json_keys_test.dart` — extended to assert `JsonKeys.message` is non-empty.
- `flutter analyze` — no issues found.
- `flutter test` — full suite passing (confirmed by you).
