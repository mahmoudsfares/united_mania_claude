# 2.2.1 — `NewsFeedCubit` and `NewsFeedState`

## What was asked

Give the feed a cubit that drives its states: `news_feed_state.dart` defining
`typedef NewsFeedState = StateResource<List<Article>>;` (the feed has one piece of state and
`StateResource` already models it, so a wrapper class adds nothing), and `news_feed_cubit.dart`
defining a `Cubit<NewsFeedState>` that starts at `init` and, on `getNews()`, emits `loading` then
whatever the repo returned. The repo arrives through the constructor, with no widgets and no
`BuildContext` in the cubit. Tests with `bloc_test` must cover loading → success and loading →
error, using both a mocked repo and the real `NewsFeedMockRepo`.

## A design decision this subtask needed

"The repo arrives through the constructor" is ambiguous once you look at what has to compile:
`NewsFeedRepo` and `NewsFeedMockRepo` share no common type. CLAUDE.md §3 rules out an abstract
repository plus implementation pair, and `NewsFeedMockRepo` (2.1.3) has no `implements`/`extends`
relationship to `NewsFeedRepo` today. Adding one retroactively does not work anyway:
`NewsFeedRepo` has a private field (`_dioClient`), and Dart cannot satisfy a private member from
another file, so `NewsFeedMockRepo implements NewsFeedRepo` would not compile even if it were the
intended design.

The test asks for the same cubit to be driven by both a mocktail mock of `NewsFeedRepo` and the
real `NewsFeedMockRepo`. Since Dart classes are not structurally typed, the only type both repos'
`getNews` methods satisfy is a function type. So `NewsFeedCubit` takes the function itself —
`Future<NewsFeedState> Function()` — instead of a repo object: `NewsFeedCubit(newsFeedRepo.getNews)`
or `NewsFeedCubit(newsFeedMockRepo.getNews)`. This adds no new class or interface — it is the same
"repo arrives through the constructor" idea narrowed to the one method the cubit actually calls —
and swapping real for mock in `core/di` (2.5.1) is still a one-line change.

## What changed

- `lib/features/news_feed/business_logic/news_feed_state.dart` — new.
  `typedef NewsFeedState = StateResource<List<Article>>;`.
- `lib/features/news_feed/business_logic/news_feed_cubit.dart` — new. `NewsFeedCubit extends
  Cubit<NewsFeedState>`, constructed with a `Future<NewsFeedState> Function()`, starting at
  `const NewsFeedState.init()`. `getNews()` emits `const NewsFeedState.loading()` then whatever the
  injected function returns. The cubit does not import either repo class, only the function shape.
- `test/features/news_feed/business_logic/news_feed_cubit_test.dart` — new. See below.
- No other file changed.

## What was tested

`test/features/news_feed/business_logic/news_feed_cubit_test.dart`, all with `bloc_test`:

- With a mocktail `MockNewsFeedRepo` (`extends Mock implements NewsFeedRepo`), passing the stubbed
  `repo.getNews` tear-off into the cubit:
  - the repo succeeds → the cubit emits loading, then success with the stubbed data.
  - the repo fails → the cubit emits loading, then error with the stubbed message
    (`AppErrorMessages.generic`, an existing constant used here only as a stand-in return value).
- With the real `NewsFeedMockRepo`, passing `NewsFeedMockRepo().getNews`:
  - the success path → the cubit emits loading, then a success state with 10 articles, checked with
    `isA<NewsFeedState>().having(...)` on `isSuccess` and `data.length` rather than full list
    equality — `Article` does not override `==`, so two independently parsed article lists are never
    `==` even with identical field values. The exact field values are already covered by
    `news_feed_mock_repo_test.dart` and `news_feed_repo_test.dart`.
  - `returnError: true` → the cubit emits loading, then an error state carrying exactly
    `NewsFeedMockRepo.errorResponseBody[JsonKeys.message]` (a plain string, so exact equality works
    here).
