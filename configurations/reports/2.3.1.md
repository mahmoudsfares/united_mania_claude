# 2.3.1 — Shared widgets

## What was asked

Per `work_breakdown.md`, build the three widgets both the news feed and news details screens will
reuse, in `core/shared_widgets/`:

- `AppNetworkImage` — shows an image from a nullable url, falling back to the placeholder asset
  when the url is null or empty, a loading indicator while fetching, and the same placeholder if
  the fetch fails.
- `AppLoader` — a centred progress indicator in the theme's colours.
- `AppErrorView` — a message plus a Retry button.

This subtask does not depend on the pagination work (Task 2.4) or on anything under
`features/news_feed/` — per the dependency map it branches directly off 1.1.1, so it only needed
the colours, theme, and strings from Task 1.2 to already exist, which they do.

## A design decision this subtask needed

`AppNetworkImage`'s placeholder image path is a string literal. CLAUDE.md §4 forbids hardcoded
strings outside their constants file, so a new `core/utils/app_images.dart` (`AppImages` class) was
added, holding `articlePlaceholder`. This wasn't in the work breakdown by name, but it's the same
pattern as `app_colors.dart`/`app_strings.dart`/etc. and is needed by this subtask itself, not a
later one.

Testing `AppNetworkImage`'s network-fetch behaviour took two attempts:

- **First attempt**: to prove the "good url" case truly renders a fetched image, I wired Flutter's
  test-only `debugNetworkImageHttpClientProvider` hook to a fake `dart:io` `HttpClient` that
  returned a real 1x1 PNG, so the image would actually decode without touching the network. You ran
  it and one test hung: `pumpAndSettle timed out`, with no other error printed. The fake's async
  chain was never completing, but nothing threw to say why — chasing that further would mean
  guessing at exactly which internal call this Flutter version's image loader makes on
  `HttpClient`/`HttpClientResponse`, with no way for me to verify a fix without another round trip.
- **Second attempt (what shipped)**: the "good url" case doesn't actually need the fetch to
  succeed — it only needs to prove `AppNetworkImage` builds an `Image.network` with the right url
  and the right `loadingBuilder`/`errorBuilder`. The test now checks that configuration directly,
  and calls `loadingBuilder` with synthetic arguments to confirm it shows `AppLoader` while loading
  and the real frame once done. No network, no fake client needed.
- The "failing url" case still exercises a **real** failure, without touching the network: the url
  `https://example.com/%` has a lone `%`, which is invalid percent-encoding, so Flutter's own `Uri`
  parsing throws inside the image loader. `errorBuilder` genuinely fires and the placeholder
  genuinely appears — this one test runs the real failure path end to end.

## What changed

New files:

- `lib/core/utils/app_images.dart` — `AppImages.articlePlaceholder`.
- `lib/core/shared_widgets/app_loader.dart` — `AppLoader`, a `Center` wrapping a
  `CircularProgressIndicator` coloured `AppColors.primary`.
- `lib/core/shared_widgets/app_error_view.dart` — `AppErrorView`, taking `message` and `onRetry`;
  a centred message plus an `ElevatedButton` labelled `AppStrings.retry`.
- `lib/core/shared_widgets/app_network_image.dart` — `AppNetworkImage`, taking a nullable `url`.
  Null/empty shows the placeholder (`Image.asset(AppImages.articlePlaceholder)`). Otherwise it
  builds `Image.network` with a `loadingBuilder` (shows `AppLoader` until the last chunk event,
  then the real frame) and an `errorBuilder` (shows the same placeholder).
- `test/core/utils/app_images_test.dart`, `test/core/shared_widgets/app_loader_test.dart`,
  `test/core/shared_widgets/app_error_view_test.dart`,
  `test/core/shared_widgets/app_network_image_test.dart`.

No existing file changed.

## What was tested

- `AppImages`: `articlePlaceholder` is non-empty and points into `assets/images/`.
- `AppLoader`: renders a `CircularProgressIndicator` inside a `Center`, coloured
  `AppColors.primary`.
- `AppErrorView`: renders the given message and the Retry label; tapping Retry calls `onRetry`.
- `AppNetworkImage`: shows the placeholder for a null url and for an empty url; falls back to the
  placeholder when a fetch genuinely fails (the malformed-url case above); for a good url, builds
  `Image.network` with that exact url, and its `loadingBuilder` shows `AppLoader` while a chunk
  event is in progress and passes the real child through once loading is done (`loadingProgress ==
  null`).
