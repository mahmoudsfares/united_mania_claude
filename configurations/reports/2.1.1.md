# 2.1.1 — `Article` and `ArticleSource` models

## What was asked

Parse the news feed API payload safely: two plain data classes, `Article` and `ArticleSource`, each
with `fromJson`/`toJson`, reading every key from `JsonKeys`. Every leaf field is `String?` because
the API returns nulls freely. Tests must cover the real sample payload from the spec, an all-null
payload, a `toJson(fromJson(x)) == x` round trip, and a missing `source` object.

## What changed

- `lib/features/news_feed/models/article_source.dart` — new. `ArticleSource` holds `id` and `name`,
  both `String?`, with `fromJson`/`toJson` reading/writing through `JsonKeys.id` / `JsonKeys.name`.
- `lib/features/news_feed/models/article.dart` — new. `Article` holds `source`, `author`, `title`,
  `description`, `url`, `urlToImage`, `publishedAt`, `content`. `source` is `ArticleSource?` rather
  than a non-nullable object: when the JSON value at `JsonKeys.source` is missing or not a map,
  `Article.fromJson` sets `source` to `null` instead of inventing an empty `ArticleSource`, which is
  what the "missing source object does not crash" test is checking for. `toJson` always writes every
  key (including a `null` for a missing `source`), so it matches how NewsAPI's own responses are
  shaped — every field present, value `null` when unknown — and that is what makes the round-trip
  test exact.
- Neither class extends `Equatable` or implements `==`. The subtask only asks for `fromJson`/`toJson`,
  and the round-trip test compares the plain `Map`s those methods produce, not model instances, so
  value equality was not needed here. Flagged under "left open" below for whoever picks up 2.2.1.
- `news_feed.md` §2 documents field-level examples (`source.name: "Yahoo Entertainment"`,
  `publishedAt: "2026-09-15T12:06:44Z"`, the `"… [+13602 chars]"` truncation marker) but not one
  consolidated JSON object. The "real sample payload" used in the tests is those documented values
  assembled into a single `Article` JSON object, with the remaining fields (`author`, `title`,
  `description`, `url`, `urlToImage`) filled with plausible United-news text consistent with what
  §2 says each field holds. No values were invented that contradict the spec.

## What was tested

- `test/features/news_feed/models/article_source_test.dart` — parses id/name; parses a null id and
  name; `toJson` round-trips `fromJson`'s output.
- `test/features/news_feed/models/article_test.dart` — parses the assembled sample payload and
  checks every field, including the nested source; round-trips that payload through
  `toJson(fromJson(x)) == x`; parses an all-null payload without throwing and checks every field
  comes back `null`; round-trips the all-null payload; parses a payload with no `source` key at all
  and checks `article.source` is `null` rather than throwing.
- Confirmed the fail-first step: you ran `flutter test test/features/news_feed/models/` before the
  `lib/` files existed and got the expected failure, then again after implementing and got a pass.
- `flutter analyze` — no issues found.
- `flutter test` (full suite) — all passing, confirmed by you.

## Anything left open

`Article` has no value equality. This subtask's own tests never needed it (they compare `Map`s, not
model instances), so none was added, per CLAUDE.md's "do not over-engineer." Sprint 2's cubit tests
(2.2.1) will emit `StateResource<List<Article>>` states and compare them; as long as those tests
reuse the same `List<Article>` instance for both what the mock repo returns and what the test
expects, identity equality is enough and nothing here needs to change. If a later subtask instead
needs to compare two separately-built `Article` lists for equality, that subtask should add
`Equatable` to both models then, rather than it having been guessed at now.
